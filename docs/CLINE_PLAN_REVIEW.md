surfaced things that could not have been guessed. Two issues below are silent
data-corruption risks, not style points.

## Correction 1 — CRITICAL: "Bulked m³" is not in-situ

The probe found the `Trench_Summary` header is:

```
Operation Group | Exported (Bulked m³) | Reused (Bulked m³) | Cut (Bulked m³)
| From Site (Compressed m³) | Imported (Banked m³) | Fill (Compressed m³)
| Site Balance (Bulked m³)
```

Three different measurement states appear in one row: **Bulked**, **Compressed**
and **Banked**. The plan records the header text but never assigns semantics to
those states, and Step 2 proceeds straight to parsers.

`earthwork.bulking_shrinkage` in Phase 1 takes `insitu_m3` as its input. Feeding
it a "Cut (Bulked m³)" figure produces a demonstrable 30% over-measure:

```
Feed bulked 1300 m3 in as in-situ (clay, BF 1.30):
  reported loose = 1690.0 m3
  true in-situ   = 1000.0 m3, true loose = 1300.0 m3
  ERROR: +30% over-measure
```

**And CheckMate passes it**, because the arithmetic is correct and the evidence
is attached. CheckMate verifies *how* a number was computed, not whether the
source column meant what the parser assumed. This is precisely the blind spot
the Step 1 stop exists to close, and the plan walked past it.

Required before any parser is written:

- State explicitly which measurement state each column is in.
- Confirm Mudshark's terms against the Phase 1 model:
  `Banked` = in-situ/undisturbed; `Bulked` = loose/after excavation;
  `Compressed` = compacted/placed.
- Decide the canonical storage state — recommend **storing in-situ (banked)**
  as the single source of truth, converting on ingest, and recording the
  original value and its state in the `EvidenceRef.raw_text` so the conversion
  is auditable.
- Add `measurement_state` as an explicit field on ingested quantities. Never let
  a bulked figure reach a tool expecting in-situ.

## Correction 2 — CRITICAL: formula cells read as None

The probe noted the summary rows are **SUM formulas**. `openpyxl` cannot
evaluate formulas. Verified:

```
data_only=True  -> TOTAL cell value: None
data_only=False -> TOTAL cell value: '=SUM(B2:B3)'
```

`data_only=True` returns the *cached* result Excel last wrote. If the file was
generated by Mudshark and never opened and saved in Excel, **there is no cache
and every total silently reads as `None`.** With `data_only=False` you get the
formula string instead of a number.

A parser that does `float(cell.value or 0)` would turn every total into `0.0`
and report it as a successfully ingested quantity.

Required:

- Never trust a formula cell. Sum the underlying data rows in Python.
- If a cached total *is* present, use it as an independent cross-check against
  the Python sum and raise a CheckMate finding on mismatch — this is a genuinely
  valuable free verification.
- Treat `None` from a numeric column as a hard parse failure, never as zero.

## Correction 3 — drop `xlwt` for fixtures

The plan proposes `xlwt` for synthetic `.xls` fixtures, with "create a minimal
BIFF8 fixture by hand" as fallback. `xlwt` is effectively unmaintained, and
hand-crafting BIFF8 bytes is a poor use of effort.

Better: commit **one tiny real `.xls`** that you have personally sanitised —
correct structure, invented numbers, no client names. That is explicitly
permitted by `docs/DATA_ONBOARDING.md`, exercises the true `xlrd` path, and
costs minutes. Generate the `.xlsx` fixtures with `openpyxl` as planned.

## Correction 4 — pin the dependency and note the xlrd limitation

`xlrd` **dropped `.xlsx` support at version 2.0** and reads only legacy `.xls`.
That is exactly what is needed here, but it must be pinned and documented so
nobody later "upgrades" the code to use `xlrd` for the `.xlsx` file:

```
xlrd>=2.0.1    # legacy .xls (BIFF8) only — .xlsx support removed in 2.0
```
